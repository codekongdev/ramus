# A5 자동 분기 연결

`execution.work_composition.build_work_execution_runtime`가 A4 실행기에 `work` 핸들러와 Task 상태 동기화를 등록한다. `handlers`에는 B 트랙의 `summary` 핸들러를 추가할 수 있다. 외부 서비스 호출은 주입한 `LlmGateway`에서만 수행한다.

## 앱 조립

조립 루트에서 다음 구현을 주입한다.

| 인자 | 제공 모듈 | 역할 |
| --- | --- | --- |
| `transaction` | shared | 호출마다 커밋·롤백하는 DB 트랜잭션 |
| `publisher` | realtime | 프로젝트 SSE 이벤트 발행 |
| `gateway`, `connections` | access/execution(A3) | 요청자의 키로 모델 호출, 키 연결 여부 조회 |
| `context_provider` | resources/sharing(B3) | 적용된 자료·결론의 고정 버전 조회, 자료 적용 목록 복사 |
| `writer` | conversations(A2) | `ConversationWriter`: 자식 대화와 AI·시스템 메시지 저장, 커밋 후 대화·메시지 이벤트 예약 |

반환한 runtime의 `requester`를 대화 서비스에 넘기고, 앱 수명주기에서 `runtime.worker.run_forever()`를 시작·종료한다. 대화 writer와 실행기는 같은 이벤트 발행기를 사용한다. 기본 `create_app()`은 `OpenAiGateway`를 감싼 `LongSummaryGateway`, 업무·결과 정리 핸들러, A2의 실제 대화 writer, B3의 실제 ContextProvider를 조립하고 worker를 시작한다. 앱 객체 생성은 DB에 연결하지 않지만 수명주기를 시작하면 worker가 DB를 조회한다.

게이트웨이는 access의 공개 `CredentialProvider`로 실행 요청자의 현재 키를 읽고, DB 트랜잭션을 닫은 뒤 Responses API를 호출한다. `OPENAI_MODEL`과 엄격한 JSON 스키마를 보내고 `store: false`를 지정한다. 응답 거절·불완전 응답·스키마 위반과 제공자 오류는 안전한 실행 오류로 변환하며 키나 제공자 본문을 저장하거나 로그에 남기지 않는다. API 키 등록에는 기존과 같이 `RAMUS_SECRET_KEY`가 필요하다. 가짜 응답은 `create_app(..., llm_gateway=...)`로 테스트에서만 명시적으로 주입한다.

Task 목록·상세·취소·재시도 HTTP API도 같은 runtime에 연결된다. 프로젝트 참여자는 작업을 읽을 수 있고, 변경은 Task 요청자와 현재 업무 Run 요청자가 모두 일치해야 한다. 다른 계정이 보완 요청을 실행한 동안 원 Task 요청자는 그 계정의 Run을 중단하거나 다시 실행할 수 없다. 변경 요청은 멱등 키를 사용하고, 조회·변경·receipt 재생 전에 프로젝트 권한을 검사한다.

## 입력과 분기

`conversations.application.work_inputs.WorkInputReader`는 실행의 원래 요청까지 메시지를 읽는다. 기본 SQL 구현은 `run_id`에 연결된 사람 메시지 또는 자식 시작용 시스템 메시지의 `seq`를 기준으로 자른다. 대기·실행 중 도착한 후속 메시지는 그 실행의 입력에 섞이지 않는다. 재시도도 같은 원래 요청을 사용하며 자료·결론 버전은 새 점유 시점에 다시 고정한다. 모델 요청의 `message_from_seq`·`message_to_seq`는 실제 자료·결론 버전 ID와 함께 Run 입력 스냅샷에 저장한다.

부모 대화의 모델 출력은 `answer`, `clarify`, `branch` 중 하나다. 방법 질문·작업 목록 작성·사람 간 배정은 분기하지 않도록 요청에 명시한다. 의미 판정은 모델이 수행하며 애플리케이션은 출력 스키마, 최대 4개 작업, 공백·대소문자만 다른 중복 목표·시작 입력을 검사한다. 자식 대화는 별도 스키마로 `branch`를 거부한다.

분기는 하나의 완료 트랜잭션에서 자식 대화, Task, 자료 핀, 자식 Run, 시스템 시작 입력과 부모의 짧은 안내를 저장한다. 목표는 Task에, 시작 입력은 자식 메시지에, 출처는 `source_run_id`·`source_conversation_id`에 남긴다. 자식 실행에는 Task의 목표를 시작 입력과 함께 전달한다. 중간 단계가 실패하면 모두 롤백되며 미완성 자식이나 생성 이벤트가 남지 않는다. 기존 A4 완료 상태 전이와 `(source_run_id, ordinal)` 고유 제약이 중복 생성을 막는다.

첫 자식은 분기 시점 부모의 정확한 자료 버전 ID를 복사한다. 이후 자식은 같은 트랜잭션에서 만든 앞 자식의 적용 목록을 복사하므로 부모가 동시에 적용 목록을 바꿔도 형제들의 초기 버전은 같다. 받은 결론은 자동 복사하지 않는다. 이후 부모의 새 버전 저장·적용도 자식 설정을 바꾸지 않는다.

## 작업 상태와 검증

현재 업무 Run의 `pending`·`running`·`succeeded`·`failed`·`cancelled`는 Task의 `pending`·`running`·`ready`·`failed`·`cancelled`로 같은 트랜잭션에서 반영된다. 재시도·대기 시간 초과·재시작 복구도 같은 경로를 쓴다. `current_run_id` 조건으로 예전 실행이 새 작업 상태를 덮지 않으며 결과 정리 Run은 업무 Task 상태를 바꾸지 않는다. `task.updated`는 results 모듈의 공개 조회 포트로 기존 결과 연결을 유지하고 커밋 후 발행한다.

로컬 검증:

```sh
uv run --project apps/api ruff check apps/api
uv run --project apps/api pytest
```

통합 테스트는 `conftest.py`가 만든 `ramus_test_*` 임시 DB를 사용한다. `test_live_gateway_integration.py`는 계정 키 저장·복호화, 기본 게이트웨이 조립, 자료 v1 고정, worker 완료까지 확인하고 제공자 HTTP만 대체한다. F-02의 여섯 사례는 FakeLLM에 정해 둔 출력을 통한 계약 검사다. 실제 모델의 의미 판정 정확도는 [실제 모델 분기 평가](#2026-11-12-실제-모델-분기-평가)에 기록한다. 실제 키·모델 호출은 로컬 검증에 포함하지 않는다.

브라우저에서 응답·분기·작업 큐·중단·재시도·부모 초안 유지·새로고침 후 저장 상태를 확인한다.

```sh
pnpm exec playwright test tests/e2e/work-execution.spec.ts
```

이 테스트는 임시 DB와 실제 API·worker·SSE를 쓰고 모델 응답만 결정적으로 주입한다. 수명주기가 필요 없는 라우터 단위 테스트는 worker를 시작하지 않아 개발 DB에 접근하지 않는다.

## 2026-11-12 실제 모델 분기 평가

F-02의 여섯 사례와 변형 문장으로 실제 모델의 분기 판정을 평가했다. 모델은 운영 기본값 `gpt-6-luna`이고, 변형 14개를 변형마다 3회씩 호출했다. 같은 평가를 두 조건으로 실행해 실제 호출은 모두 84회였다.

- 자료 없음: 새 대화처럼 적용한 자료가 없다.
- 기본 정보 적용: 공동 샘플의 시드 자료 `가상 서비스 기본 정보` v1을 대화에 적용했다. 생활용품 쇼핑몰이라는 업무 맥락과 비교용 가상 쇼핑몰 A·B·C가 이 자료에 들어 있다.

### 평가 방법

평가 스크립트는 운영과 같은 `WorkPurposeHandler`, `LongSummaryGateway(OpenAiGateway)`, 출력 스키마 검증, worker와 같은 120초 제한과 오류 코드 변환을 사용한다. 대화 입력, 작업 저장, 자식 대화·Run 생성만 메모리 구현으로 바꾸었다. 그래서 DB를 사용하지 않았고 개발 데이터에도 접근하지 않았다. 작업 수는 모델 출력이 아니라 handler가 실제로 저장한 Task로 센다. DB 트랜잭션과 SQL 입력 조회는 기존 통합 테스트와 2026-11-10 실제 확인이 맡는다.

판정 기준은 다음과 같다.

- 작업 없음(F02-1~4): 작업을 하나라도 만들면 불필요한 분기다. `answer`와 `clarify`는 통과다.
- 실행(F02-5): `answer`이거나 작업 1~4개로 분기하면 통과다. 목적과 범위를 준 요청이므로 `clarify`는 실행 보류로 따로 센다.
- 명시 범위 분할(F02-6): 가입·혜택·해지 작업이 하나씩 정확히 세 개 생기면 통과다. 작업이 없으면 분기 누락이고, 개수나 범위가 다르면 범위 불일치다. 범위는 작업 제목(없으면 목표)의 낱말로 판정하며 `탈퇴`도 해지로 본다.
- `@AI`가 없는 원문(F02-1~3)은 운영에서 Run을 만들지 않으므로 모델을 호출하지 않는다. 이 항목은 `mentions_ai` 규칙을 확인하는 결정적 검사다.

- `@AI`가 없는 원문 3개는 두 조건 모두 Run을 만들지 않았다(3/3).
- 불필요한 분기는 두 조건 모두 0회다. 방법 질문에 범위를 나열한 `@AI 가입·혜택·해지 벤치마킹은 어떻게 나눠서 하면 좋을까?`도 6회 모두 작업을 만들지 않았다.
- 분기 누락은 자료 없음에서 9회, 기본 정보 적용에서 5회였다. 기본 정보 적용의 F02-6 변형별 통과는 `가입·혜택·해지로 … 나눠 진행해줘` 2/3, `가입, 혜택, 해지 세 범위로 나눠서` 0/3, 앞선 논의 뒤 `이 세 범위로 … 나눠 진행해줘` 2/3이다.
- 분기한 4회는 모두 `가입 벤치마킹`·`혜택 벤치마킹`·`해지 벤치마킹` 세 작업을 만들었고 범위 불일치는 없었다. 부모에는 `별도 작업 3개로 나눠 진행합니다.`만 남았다. 시작 입력에는 고정 자료의 버전 ID를 출처로 적고, 자료에 없는 정책은 미확정으로 표시하라고 썼다.
- 제공자 오류와 출력 스키마 오류는 없었다.

### 실패 원인

실패는 모두 실행 요청을 `clarify`로 보류한 경우다.

- 자료 없음: 15회 모두 대상 업종·서비스나 비교할 경쟁사를 되물었다. 새 대화의 요청에는 프로젝트 이름이나 설명이 들어가지 않아서, 모델이 `타사`의 범위를 정할 근거가 없다고 판단했다.
- 기본 정보 적용: 보류한 11회는 비교할 A·B·C의 정책 자료가 없다는 점을 들거나, 자료의 "A·B·C는 가상 사례이며 실제 타사 정책을 쓰지 않는다"는 문장과 `타사 조사` 요청이 충돌한다고 보았다. 그래서 비교할 자료를 요청하거나 실제 경쟁사를 조사할지 가상 사례를 비교할지 물었다.
- 공통: `WORK_RULES`는 "목표와 범위가 충분하면 실행"이라고만 쓴다. 비교 대상과 세부 기준을 고르는 일이 AI의 몫이라는 F-02 원칙과, 자료가 부족할 때 가정과 미확인 항목을 밝히고 진행하는 방법은 지시하지 않는다. 실행 경로에 웹 조사 도구가 없고 "제공된 버전의 자료와 결론만 사용"하라는 규칙이 있어서, 모델이 조사할 근거가 없다고 판단하는 것으로 추정한다. 이 추정은 지시문을 보완한 뒤 재평가로 확인해야 한다.

### 후속 조치

1. `WORK_RULES` 보완은 별도 변경으로 진행한다. 명시적인 실행 요청이면 비교 대상·기준·작업 구조는 AI가 정하고, 그 가정은 시작 입력에 적는다. 자료가 부족한 것은 `clarify` 사유가 아니며 미확인으로 표시한다. 사용자가 범위를 나열해 나눠 진행하라고 하면 그 범위대로 분기한다. `clarify`는 요청 목적 자체를 알 수 없을 때만 쓴다. 보완한 뒤에는 같은 스크립트로 두 조건을 다시 실행해 F02-1~4의 불필요한 분기가 0인지와 F02-5·6의 통과율을 확인한다.
2. 실행 경로에 웹 조사 도구가 없는 상태에서 `타사 조사`의 결과물을 정해야 한다. 모델의 일반 지식을 출처 표시와 함께 쓸지, 자료가 없으면 비교 기준과 조사 계획만 만들지는 제품 결정이 필요하다. 이 결정에 따라 F02-5의 통과 기준을 실행 여부에서 산출물 내용까지 넓힌다.
3. 평가 세트에 조건을 더 넣는다. A·B·C 조사 결론을 공유받은 시연 설계 대화와, 로드맵 9.4의 영어 요청문이 대상이다.

### 한계

- 합성 문장 14개를 한 모델로 변형마다 3회씩만 호출했다. 통과율은 경향을 보여 주는 값이며 통계적으로 확정한 정확도가 아니다.
- DB, worker, 자식 Run 실행은 포함하지 않았다. 분기 뒤 자식 작업의 결과 품질도 평가하지 않았다.
- F02-5는 실행했는지만 판정하고 답변 내용의 품질은 보지 않는다. F02-6의 범위 판정은 낱말 일치이므로, 통과한 4회의 작업 제목·목표는 보고서에서 직접 확인했다.

### 실행 방법

```sh
pnpm api:eval-branch --mode fake
uv run --project apps/api python apps/api/scripts/eval_auto_branch.py --mode live --env-file <키 파일>
uv run --project apps/api python apps/api/scripts/eval_auto_branch.py --mode live --context service-brief --env-file <키 파일>
```

- 스크립트는 `apps/api/scripts/eval_auto_branch.py`이고, 사례와 판정 규칙은 `branch_eval_cases.py`에 있다. 공급자 없이 실행하는 fake 모드와 판정 규칙은 단위 테스트(`test_branch_eval_script.py`)로 검사한다.
- 실행 전에 호출 계획을 출력하고, `--max-calls`(기본 60)를 넘으면 키를 읽거나 호출하기 전에 멈춘다. `--cases`, `--trials`로 범위를 줄일 수 있다.
- live 모드는 `--env-file`에서 `OPENAI_API_KEY`만 읽고 키와 제공자 원문을 출력·저장하지 않는다. `pnpm`으로 `--env-file`을 넘기면 `pnpm`이 그 옵션을 가로채 파일 전체를 환경 변수로 읽으므로 live 모드는 `uv run`으로 직접 실행한다. 이번 첫 실행은 `pnpm`을 거쳤지만 키 파일에 `OPENAI_API_KEY` 한 항목만 있어 다른 설정은 섞이지 않았다.
- 보고서는 `artifacts/branch-eval/`(Git 제외)에 쓰고, 중단되면 그때까지의 결과를 `complete: false`로 남긴다. 이번 평가의 로그와 보고서에는 키 형식 문자열이 없었다.
