## 1. 한눈에 보기

| 단계 | 목표 | 진행 방식 | 끝나는 조건 |
|---|---|---|---|
| Phase 0. 기반·계약 | 두 사람이 서로 기다리지 않을 기반을 만든다 | 계약 회의(반나절) 후 역할을 나눠 구현 | 두 계정이 로그인해 같은 공동 샘플의 빈 3단 화면을 보고, 계약·스키마·포트·이벤트 목록이 main에 있음 |
| Phase 1. 기능 트랙 | 업무 영역별로 기능을 수직으로 나눠 동시에 만든다 | 트랙 A 메이슨, 트랙 B 헤이든 | 동기화 지점 S1~S3 통과 |
| Phase 2. 통합·시연 | 시연 흐름을 실제 서버에서 끝까지 실행한다 | 함께 | 시연 E2E와 ON-AC 전체 통과, 화면별 스크린샷 확인 |
| Phase 3. 선택 기능 | 시연 이후 기능을 추가한다 | 여유에 따라 | 별도 판단 |
| Phase 4. 다국어 | 영어 화면을 추가한다(9장) | 공용 부분은 소유권대로 나누고 기능 문구는 트랙별로 옮긴다. 준비 규칙(9.3)은 Phase 1부터 지킨다 | 9.6 완료 기준 통과 |

트랙은 프론트엔드·백엔드가 아니라 업무 영역으로 나눴다. 각자 맡은 영역의 API·DB·화면·테스트를 모두 책임지므로, 계층으로 나눌 때보다 통합을 기다리는 시간이 줄어든다.

- **트랙 A (메이슨): 접근·대화·AI 실행.** 로그인과 공동 샘플 참여, 대화와 실시간 반영, API 키 연결, 실행기, 자동 분기, 작업 큐, 작업 모달의 틀과 대화 탭, 프로젝트 관계 보기.
- **트랙 B (헤이든): 자원·결과·연결.** 공통 스킬·자료와 버전 관리, AI 입력 조립, 결과 정리와 버전, 결론 보기, 다른 대화에 보내기, 결과로 새 대화, 결과물 목록(조회 전용), 시드 콘텐츠.

와이어프레임의 사용 흐름 8개는 아래와 같이 나뉜다.

| 와이어프레임 흐름 | 화면 | 트랙 |
|---|---|---|
| ① 팀과 논의하고 조사 맡기기 | 01·02·03 | A |
| ② 끝난 조사를 검토하고 결과 정리하기 | 04·05 → 06·15 | A → B |
| ③ 결론을 다른 대화에 보내기 | 08·07·15 | B |
| ④ 결과로 새 대화 만들어 이어가기 | 08·11·12 | B |
| ⑤ 함께 쓸 업무 기준 준비하기 | 14·10 → 01 | B → A |
| ⑥ 프로젝트 전체 관계 살펴보기 | 13·05 | A |
| ⑦ 결론만 읽고 돌아가기 | 08·16 | B |
| ⑧ 공통 기준을 수정하고 버전 적용하기 | 17·18·19 | B |

트랙 A에는 실행기·동시성·키 보안처럼 위험이 큰 부분을 모았다. 저장소의 기존 설정을 만든 메이슨이 맡는 안을 권장하지만, 두 사람의 숙련 영역에 따라 트랙을 서로 바꿔도 구조는 그대로 유지된다.

## 2. 시연 장면과 기능 매핑

구현 순서는 90초 시연을 실제 서버에서 끝까지 실행하는 것을 기준으로 정한다.

| 시연 구간 | 장면 | 필요한 기능 | 트랙 |
|---|---|---|---|
| 0–15초 | 메신저로 결과와 스킬 파일을 받아 개인 AI에 넣는 기존 방식 | 제품 기능이 아님. 시연용 장면을 따로 준비 | Phase 2 |
| 15–30초 | 공통 스킬을 적용하고 보내 둔 조사 결과를 입력으로 삼아 A·B가 같은 대화에서 @AI에 질문 | F-08·F-09 버전 고정 적용, F-06 보내기(입력 자동 연결), F-01 대화, 실시간 반영, 계정별 키 | A·B |
| 30–50초 | 경쟁사 비교·반품 예외 검토를 별도 작업으로 진행하고 팀은 논의를 계속 | F-02 자동 분기, F-03 큐, 부모 대화 비잠금 | A |
| 50–70초 | 담당자가 결론을 정리·저장해 통합 대화로 보내고, 통합 대화에서 두 결론으로 구성안 정리 | F-04 작업 모달, F-05 결론 정리·버전, F-06 다른 대화에 보내기 | A·B |
| 70–90초 | 화면·정책 담당자가 각자 같은 구성안 결론을 열어 새 대화를 만들고 상세 기획 시작 | F-07 결론 보기에서 새 대화 만들기 | B |

시연 문서는 "조사 결과를 선택한다"고 표현하지만, 와이어프레임 기준에서는 결과를 받는 대화에서 고르지 않고 보내는 사람이 ‘다른 대화에 보내기’로 연결한다. 시연 대본은 이 흐름에 맞춰 다듬는다.

시연 데이터는 기획서 9.2의 공동 샘플(쇼핑몰 멤버십 도입)로 준비한다. 계정 세 개 이상이 같은 공간에 동시에 접속하는 상황이 시연과 심사 검증(ON-AC)의 기본 조건이다.

## 3. Phase 0에서 고정할 기술 결정

아래 결정은 두 트랙이 함께 의존하므로 Phase 0 계약 회의에서 확정하고, 이후에는 6.3의 계약 변경 절차로만 바꾼다.

| 영역 | 결정안 | 이유 |
|---|---|---|
| 서버 구성 | FastAPI 단일 프로세스 Modular Monolith. 실행기도 같은 프로세스의 asyncio 작업자로 시작한다 | CONVENTIONS의 모듈 구성과 맞고 배포가 단순하다. 분리가 필요해지면 실행기만 Worker로 옮긴다 |
| 실시간 | 프로젝트 단위 SSE(`GET /api/projects/{id}/events`). 재접속하면 서버 상태를 다시 읽는다 | 서버에서 클라이언트로 가는 단방향 이벤트로 충분하다. 9.5의 재접속 복구 규칙과 맞다 |
| AI 응답 | 스트리밍하지 않는다. 실행 중에는 run 상태만 표시하고, 응답이 끝나면 메시지로 저장해 발행한다 | 기획서에 스트리밍 요구가 없고 동시성 처리가 단순해진다 |
| 실행 상태 | `run`·`task` 테이블이 원본이다. 대기 실행은 `FOR UPDATE SKIP LOCKED`로 점유하고 진행 중 실행은 heartbeat로 관리한다. 서버가 재시작되면 heartbeat가 끊긴 실행을 재시도 가능한 failed로 바꾼다 | pending 무기한 대기 금지(F-03)와 재시작 복구 |
| 대화별 실행 제한 | `run.conversation_id`에 활성 상태(pending·running) 부분 고유 인덱스를 둔다 | 같은 대화의 AI 실행을 하나로 제한하는 규칙(9.5)을 DB가 보장한다 |
| 멱등 | 변경 요청은 `Idempotency-Key` 헤더를 받고 처리 결과를 receipt 테이블에 저장한다 | 메시지·분기·공유의 중복 생성 방지(ON-AC-09) |
| 결과·공통 자료 버전 | 결과 버전과 공통 자료 버전 모두 기준 버전을 포함한 조건부 저장을 쓴다. 충돌하면 409를 반환하고 클라이언트는 입력 초안을 유지한다. 저장한 버전은 수정하지 않는다 | CONVENTIONS의 낙관적 잠금, AC-19 |
| 버전 고정 | 대화는 공통 자료를 자원 ID가 아니라 **버전 ID**로 참조한다. 받은 결론도 결과 버전 ID로 연결한다. "최신 버전"으로 자동 해석하는 경로를 만들지 않는다 | F-09, AC-15·17 |
| 실행 입력 스냅샷 | Run을 시작할 때 실제 사용한 자원 버전 ID·결과 버전 ID 목록을 Run에 기록한다. 실행 중 설정이 바뀌어도 스냅샷은 바뀌지 않는다 | F-09 실행 중 규칙, 재현 가능성 |
| API 키 | 서버 비밀값(`RAMUS_SECRET_KEY`)으로 암호화해 저장한다. 응답·이벤트·로그에는 연결 여부만 내보내고, Run에는 키 소유 계정 ID만 기록한다 | 9.4, ON-AC-07·08 |
| 로그인 | 6자리 이메일 인증코드(해시 저장, 만료, 재전송 제한)와 httpOnly 세션 쿠키. 메일 발송은 `Mailer` 포트로 분리하고 개발 환경에서는 서버 로그에 출력한다 | 발송 서비스는 D3에서 결정 |
| 모델 호출 | `LLMGateway` 포트에 OpenAI 어댑터와 결정적 응답을 주는 `FakeLLM`을 둔다. 자동 분기 판단은 JSON 스키마 출력으로 받아 경계에서 검증한다 | 테스트·E2E에서 비용 없이 같은 흐름을 검증한다 |
| AI 입력 조립 | 대화 메시지, 적용한 자원 버전, 연결된 결론 버전 스냅샷으로 모델 입력을 만드는 순수 함수 | Functional Core. 단위 테스트로 검증한다 |
| 결과 정리 출력 | 모델 출력 스키마의 사용자 본문 필드는 `conclusion` 하나다. 원문 메시지 범위와 사용한 자료 버전은 시스템이 별도 메타데이터로 저장한다 | F-05, AC-08 |
| 프론트 상태 | 기능별 MVI(useReducer + EffectHandler). SSE 이벤트도 Intent로 Reducer에 전달한다 | 서버 상태를 원본으로 삼는다(CONVENTIONS) |
| API 타입 | `contracts/openapi.json`에서 `openapi-typescript`로 생성한다. 생성 파일은 손으로 고치지 않는다 | OpenAPI 기준 계약 |

## 4. 모듈과 소유권

### 4.1 백엔드 모듈

`apps/api/src/ramus_api/modules/<모듈>/` 아래에 domain·application·infrastructure·presentation을 둔다. 다른 모듈은 공개 인터페이스로만 호출하고 상대 모듈의 테이블을 직접 수정하지 않는다.

| 모듈 | 테이블 | 소유 | 다른 트랙에 제공하는 공개 인터페이스 |
|---|---|---|---|
| access | account, membership, email_code, session, ai_connection | A | 현재 사용자, 프로젝트 권한 확인, 계정별 자격증명 조회(실행기 전용) |
| projects | project | A | 프로젝트 조회, 생성 권한이 있는 프로젝트 검색 |
| conversations | conversation, message | A | 대화 생성(최상위·자식), 메시지 조회, 제목 검색 |
| execution | run, task | A | 실행 등록(목적: 업무·결과 정리), 실행 상태 조회 |
| realtime | 없음 | A | 이벤트 발행 |
| resources | resource, resource_revision, conversation_resource | B | 대화에 적용한 자원 버전 조회·복사(분기 상속), AI 입력용 자원 버전 내용 조회 |
| results | result, result_revision | B | 승인 버전 조회 |
| sharing | share, conversation_input | B | 대화에 연결된 결론 버전 스냅샷 조회, 결론에서 새 대화 생성 |
| seed | seed_marker | A(고정 프로젝트·참여 등록), B(콘텐츠) | 시드·리셋 명령 |

트랙 사이의 의존은 세 군데다. 실행기(A)는 AI 입력을 만들 때 자원 버전·결론 스냅샷(B)을 읽고, 결과 정리(B)는 실행기(A)에 실행을 등록한다. 관계 보기(A)는 결론 사용 관계(B)를 읽는다. 앞의 두 인터페이스는 Phase 0에서 `ContextProvider`(B 구현)와 `RunRequester`(A 구현) 포트로 정의하고, 결론 사용 관계는 sharing 모듈의 조회 함수로 제공한다. 상대 구현이 병합되기 전에는 가짜 구현으로 개발하고 테스트한다.

### 4.2 프론트엔드 폴더

| 위치 | 소유 | 내용 |
|---|---|---|
| `src/app/` | 헤이든(Phase 0) | 라우팅, 3단 레이아웃 슬롯, 모달 호스트, 세션 확인 |
| `packages/design-system/` | 메이슨 | 디자인 시스템 원본 소스. 수정 내용은 `CHANGES.md`에 기록 |
| `src/ui/` | 메이슨(세팅), 이후 공용 | 디자인 시스템 연결 계층. 컴포넌트 재export, `UiProvider`, 일반 모달 `Dialog`, 글꼴 `overrides.css` |
| `src/lib/` | 헤이든(Phase 0) | API 클라이언트, SSE 연결·재접속, MVI 도우미, 이벤트 타입 |
| `src/features/auth`, `conversation`, `task-queue`, `task-modal`, `ai-connection`, `projects`, `project-map` | A | 로그인, 대화 트리·본문·입력창, 오른쪽 작업 큐, 작업 모달 틀과 대화 탭, 키 연결, 프로젝트 전환, 관계 보기 |
| `src/features/resources`, `results`, `sharing`, `results-library` | B | 스킬·자료 모달(검색·등록·상세/이력·수정), 결론 보기·편집, 보내기와 새 대화 화면, 왼쪽 결과물 목록과 오른쪽 공유받은 결과 |

작업 모달은 A가 틀(헤더·탭·닫기)과 대화 탭을 만들고, B가 결과 탭에 들어가는 결론 보기 컴포넌트와 헤더의 ‘결과 정리’ 액션을 만든다. 같은 결론 보기 컴포넌트는 받은 결론을 여는 모달(WF-08)에서도 재사용한다. 모달이 결과 탭과 헤더 액션을 받는 props는 Phase 0에서 정한다.

와이어프레임의 모달은 모두 **모달 위에 모달을 띄우지 않고 같은 모달의 본문만 전환한다.** 결론 보기 → 보내기·새 대화, 스킬 목록 → 등록·상세/이력·수정이 여기에 해당한다. `src/ui/Dialog` 하나 안에서 화면 단계를 상태로 바꾸는 방식으로 구현하고, 뒤로가기는 이전 단계로 돌아간다.

### 4.3 디자인 시스템 사용 규칙

- 기능 화면은 `src/ui/`에서만 컴포넌트를 import한다. `@ramus/design-system`을 기능 폴더에서 직접 import하지 않는다.
- 앱은 `UiProvider`로 감싸며 테마는 라이트, 대비는 `enhanced`로 고정한다.
- 색·간격·글꼴·모서리는 디자인 시스템의 CSS 변수(`--background`, `--foreground`, `--border`, `--primary` 등)로만 지정한다. 기능 폴더에는 레이아웃 스타일만 둔다.
- 글꼴은 라틴 문자에 Inter, 한글에 Pretendard를 쓴다. 설정은 `src/ui/overrides.css` 한 곳에만 둔다.
- 디자인 시스템에 없는 공용 컴포넌트가 필요하면 기능 폴더가 아니라 `src/ui/`에 추가한다. 일반 모달은 `src/ui/Dialog`를 쓴다.
- `packages/design-system/` 원본을 고쳐야 하면 메이슨에게 알리고 `CHANGES.md`에 기록한다.
- 디자인 시스템의 컴포넌트 목록과 미지원 범위는 `packages/design-system/COMPONENT-COVERAGE.md`에서 확인한다. 개발 서버의 `/__catalog`에서 실제 렌더를 볼 수 있다.

## 6. 협업 규칙

### 6.1 브랜치와 PR

- main에서 짧게 브랜치를 만든다. 이름은 `a/A3-ai-connection`, `b/B5-share`처럼 트랙과 작업 ID를 붙인다.
- PR 하나에는 작업 ID 하나를 담는다. 커밋 메시지는 `feat(results): ... [B3]` 형식을 쓴다.
- 리뷰는 상대가 한다. 상대 트랙의 코드를 읽어 두면 통합 지점의 오류를 일찍 발견할 수 있다.
- squash 병합 후 브랜치를 지운다. 하루 넘게 병합하지 못한 브랜치는 main에 맞춰 rebase한다.

### 6.2 하루 운영

- 시작할 때 10분 동안 오늘 작업 ID, 공용 파일 수정 계획, 막힌 지점을 공유한다.
- 공용 파일을 수정하는 PR은 그날 안에 병합한다.
- AI 에이전트에 작업을 맡길 때는 작업 ID, 소유 파일, 검증 명령, 관련 AC를 함께 전달한다(AGENTS.md). 에이전트가 상대 트랙의 파일을 수정하지 않도록 4장의 소유권을 지시문에 적는다.

### 6.3 계약 변경 절차

1. 엔드포인트·이벤트·테이블 변경이 필요하면 계약만 바꾸는 작은 PR을 먼저 올린다.
2. 상대가 확인하면 병합하고, 상대는 바로 rebase해 생성 파일을 다시 만든다.
3. 구현은 그다음 PR에서 진행한다.

### 6.4 완료 기준

- PR 설명에 관련 AC·ON-AC ID를 적고, 각 항목을 검증한 테스트를 연결한다.
- Reducer·Domain은 단위 테스트, 저장소·외부 연결은 통합 테스트, 사용자 흐름은 E2E로 변경 범위에 맞게 검증한다. 새 코드의 커버리지는 80% 이상을 목표로 한다.
- `pnpm verify`가 통과하고 OpenAPI 생성 결과에 차이가 없어야 한다.
- 실행하지 않은 검증은 통과로 적지 않는다.

## 9. 다국어 계획

MVP와 시연은 한국어로만 진행한다. 영어 화면은 시연이 끝난 뒤 Phase 4에서 추가하고, 나중에 고치기 어려운 부분만 Phase 1부터 9.3의 규칙으로 미리 막아 둔다. 이 장은 권장안이며 9.7의 결정 항목이 정해지면 확정한다.

### 9.1 범위

| 구분 | 대상 | 처리 |
|---|---|---|
| 화면 문구 | 기능 화면의 버튼·라벨·안내·빈 상태·확인 문구, 접근성 이름(`aria-label`) | 번역한다 |
| 디자인 시스템 기본 문구 | `packages/design-system/CHANGES.md`에서 한국어로 바꾼 기본 prop 값(취소·닫기·검색 등) | `src/ui/`에서 현재 언어의 문구를 넘긴다 |
| 서버 문장 | 오류 응답의 `message`, 인증 메일 | 요청 언어로 만든다 |
| 형식 | 날짜·시간·상대 시간·숫자, `Calendar`의 `locale` | `Intl`로 언어에 맞게 표시한다 |
| AI 출력 | @AI 응답, 자동 분기 안내와 작업 제목·목표, 결론 | 번역하지 않고 9.4의 언어 규칙을 따른다 |
| 사용자 콘텐츠 | 메시지, 대화·프로젝트 제목, 스킬·자료, 결론 편집본 | 번역하지 않고 입력한 언어 그대로 보여 준다 |
| 시드 콘텐츠 | 공동 샘플(쇼핑몰 멤버십 도입) | 한국어만 둔다(D14) |

실시간 이벤트에는 식별자와 상태만 담기므로(부록 B) 다국어 때문에 바꿀 부분이 없다. 사용자 콘텐츠 자동 번역, 언어별 URL, 오른쪽에서 왼쪽으로 쓰는 언어(RTL), 번역 관리 도구 연동, 한국어·영어 외 언어는 이 계획에 넣지 않는다.

### 9.2 언어 결정 방식

- 지원 언어는 `ko`(기본)와 `en`이다.
- 화면 언어는 계정 설정(`account.locale`), 브라우저 언어(`navigator.languages`), `ko` 순서로 정한다. 로그인 전에는 브라우저 언어를 쓰고, 처음 로그인할 때 그 시점의 화면 언어를 계정에 저장한다. 이후에는 상단 계정 메뉴에서 바꾼다.
- 언어는 계정마다 따로 정한다. 같은 대화에 참여한 사람들이 서로 다른 언어의 화면을 보더라도, 메시지와 결론은 모두 같은 원문을 본다.
- 프론트는 모든 API 요청에 현재 화면 언어를 `Accept-Language`로 보낸다. 서버는 이 헤더로 문장의 언어를 정하고, 헤더가 없거나 지원하지 않는 언어면 `ko`를 쓴다. 서버가 계정 설정을 따로 읽지 않으므로 응답 문장의 언어는 항상 화면 언어와 같다.
- URL에는 언어를 넣지 않는다. 로그인한 뒤에만 쓰는 화면이라 검색 노출을 고려할 필요가 없다.
- 언어를 바꾸면 `<html lang>`도 함께 바꾼다. 스크린리더의 발음과 줄바꿈 규칙이 이 값을 따른다.

### 9.3 Phase 1부터 지킬 준비 규칙

나중에 바꾸려면 저장된 데이터를 옮기거나 모든 화면 파일을 다시 열어야 하는 부분만 지금 규칙으로 정한다. 영어 문구는 아직 작성하지 않는다.

1. **사용자에게 보여 줄 문장을 DB에 저장하지 않는다.** 실패 정보는 `error_code`와 필요한 매개변수로 저장하고, 응답을 만들 때 문장으로 바꾼다. 계약 v1.1에서 `run`·`task`·`result_draft`의 실패 정보를 `error_code`와 `error_params`(JSONB)로 정했다. 운영용 상세 원인은 서버 로그에만 남긴다.
2. **서버 문장은 코드별 문구표에서 만든다.** P0-A1의 HTTP 상태별 문구처럼, 기능별 오류 문구도 모듈 코드 곳곳에 쓰지 않고 오류 코드를 키로 하는 문구표에 모은다.
3. **화면 문구는 기능 폴더의 `messages.ts`에 모은다.** 컴포넌트와 Reducer에서 문장을 직접 만들지 않는다. 값이 들어가는 문구는 문자열을 이어 붙이지 않고 매개변수를 받는 함수로 만든다. 언어마다 어순이 다르고, 한국어의 을/를·이/가처럼 앞 단어의 받침에 따라 바뀌는 조사도 함수 안에서 처리해야 하기 때문이다.
4. **날짜·시간·숫자는 `src/lib`의 형식 도우미로만 표시한다.** 도우미는 `Intl`을 쓰고 언어를 인자로 받는다. 화면에서 날짜 문자열을 직접 조립하지 않는다.

규칙 3은 `pnpm verify`(P0-B5)에 기능 폴더 `.tsx` 파일의 한글 문자열 리터럴을 찾는 검사를 넣어 지킨다. 규칙 1·2는 계약 변경과 코드 리뷰로 확인한다.

### 9.4 AI 출력의 언어

- AI는 요청 메시지와 같은 언어로 답하고, 요청한 계정의 화면 언어는 따르지 않는다. 화면 언어가 다른 사람들이 함께 쓰더라도 대화 하나의 언어가 섞이지 않게 하기 위해서다.
- 자동 분기 안내(`reply`), 작업 제목·목표, 결과 정리의 `conclusion`도 같은 규칙을 따른다. 결과 정리는 정리 대상 대화에서 주로 쓴 언어로 작성한다.
- 이 규칙은 모델 지시문에 한 줄로 넣고, 모델 출력 스키마는 바꾸지 않는다.
- 자동 분기 평가 세트(F-02의 6개 사례)에 영어 요청문을 추가한다. 영어 요청에서도 방법 질문·목록 작성·사람 간 배정을 분기로 처리하지 않는지 확인한다.
- `@AI` 호출 표기는 언어와 관계없이 같다.

### 9.5 Phase 4 작업

시연(Phase 2)이 끝난 뒤 진행한다. 공용 부분은 4장의 소유권대로 나누고, 기능 화면의 영어 문구는 각 트랙이 자기 화면을 맡는다.

| ID | 담당 | 작업 | 끝나는 조건 |
|---|---|---|---|
| L0 | 함께 | 계약 변경: `Me.locale`, 언어 변경 API(`PATCH /api/me`), `account.locale` 컬럼, 모든 요청의 `Accept-Language` 처리 규칙 | 계약 PR 병합, OpenAPI 생성 결과 갱신 |
| L1 | 메이슨 | 서버 다국어: `Accept-Language` 해석, 오류 문구표의 `en` 추가, 인증 메일 두 언어, 언어 변경 API | 두 언어 문구표의 키가 같은지 확인하는 단위 테스트, 언어별 오류 응답 통합 테스트 |
| L2 | 헤이든 | `src/lib/i18n`: 현재 언어 상태와 전환, 문구 조회, `<html lang>` 갱신, API 클라이언트의 `Accept-Language`, 공통 오류 문구, 형식 도우미와 언어 연결 | Reducer·도우미 단위 테스트 |
| L3 | 메이슨 | `src/ui/`: 디자인 시스템 기본 문구를 현재 언어로 넘기는 연결, `Calendar` `locale` 연결 | `/__catalog`를 두 언어로 열어 스크린샷 확인 |
| L4 | 각 트랙 | 기능 화면 영어 문구: 4.2의 소유권대로 각 `messages.ts`에 `en` 추가. 상단 계정 메뉴의 언어 전환은 A가 맡는다 | `en` 객체가 `ko`와 같은 타입을 만족함(누락 키는 타입 오류) |
| L5 | A·B | AI 언어 규칙: 실행·자동 분기 지시문과 영어 평가 세트(A), 결과 정리 지시문(B) | 평가 세트를 실제 모델로 1회 실행하고 결과 기록 |
| L6 | 함께 | 검증: 영어 계정으로 시연 흐름 E2E, 한국어 계정과 영어 계정이 같은 대화를 쓰는 E2E, 화면별 영어 스크린샷(1440) | 9.6 완료 기준 통과 |

진행 순서는 L0 → L1·L2·L3 → L4·L5 → L6이다. 영어 문구는 한국어보다 길어지는 경우가 많으므로, L4에서 버튼·작업 큐 제목·모달 헤더가 넘치거나 잘리지 않는지 화면에서 함께 확인한다.

### 9.6 완료 기준

- 영어 계정은 로그인 화면부터 결론 보기까지 한국어 화면 문구를 보지 않는다. 사용자 콘텐츠와 시드 콘텐츠는 예외다.
- 한국어 계정과 영어 계정이 같은 대화에 있을 때 각자 자기 언어의 화면을 보고, 메시지와 결론은 같은 원문을 본다.
- 오류 응답과 인증 메일이 요청 언어로 나온다. 다른 계정의 요청으로 저장된 실패 정보도 보는 계정의 언어로 표시된다.
- 날짜와 시간이 언어별 형식으로 표시된다.
- 한글 리터럴 검사와 두 언어의 키 비교 테스트가 `pnpm verify`에 포함되어 통과한다.
